# ccpm: model context for Ask Me

Use this block as the authoritative **user-facing** summary. Do not infer beyond it.

## What ccpm is

- **ccpm** (Claude Code Profile Manager) is a **local-only** Go CLI. It is not a fork of Claude Code, not an IDE extension, and does not collect telemetry or make network calls for its own operation.
- Isolation is via **`CLAUDE_CONFIG_DIR`**: each profile uses `~/.ccpm/profiles/<name>/` as the config root when you `ccpm run <name>` or `ccpm use <name>`.
- Shared content lives under **`~/.ccpm/share/`** (skills, MCP JSON fragments, settings fragments, etc.). Profiles typically **symlink** shared assets; MCP and settings are **merged** into launch-ready files.

## Running profiles in parallel (core use case)

- ccpm's headline feature is running **two or more Claude Code accounts at the same time**, fully isolated. Each profile uses its own `CLAUDE_CONFIG_DIR` (`~/.ccpm/profiles/<name>/`), so simultaneous sessions never share credentials, settings, MCP servers, or memory.
- To run two profiles **simultaneously**, open two terminals and run `ccpm run <profileA>` in one and `ccpm run <profileB>` in the other. They run side by side — no logging out, no swapping config files.
- Works the same for **OAuth** and **API key** profiles. Each OAuth profile authenticates independently via `claude /login` in its own profile context (macOS keychain isolation needs Claude Code v2.1.56+).
- `ccpm run <name>` needs no shell setup and is the simplest way to launch a specific profile. `ccpm use <name>` instead sets the active profile for a whole shell session (requires the shell hook from `ccpm shell-init`).

## Install

- **npm**: `npm i -g @ngcodes/ccpm`
- **curl**: `curl -fsSL https://raw.githubusercontent.com/nitin-1926/claude-code-profile-manager/main/scripts/install.sh | sh`
- **go**: `go install github.com/nitin-1926/claude-code-profile-manager/ccpm@latest`

## Real top-level commands

These are the exact commands the CLI registers. Do not invent flags or commands beyond this list.

- **Profile lifecycle**: `ccpm add`, `ccpm remove` (alias `rm`), `ccpm rename`, `ccpm clone`, `ccpm list` (alias `ls`, `--json` for machine-readable output), `ccpm status` (`--json`), `ccpm use`, `ccpm run`, `ccpm sync` (`--dry-run` previews what would link/adopt).
- **Defaults / IDE**: `ccpm set-default`, `ccpm unset-default`.
- **Shell prompt**: `ccpm prompt` (prints the active profile name for PS1/starship/p10k; supports `--format` and `--show-default`).
- **Backup / migrate**: `ccpm export <profile>` (writes a `.tar.gz`; `-o`/`--output`, `--include-history`, `--include-credentials`) and `ccpm import-bundle <file.tar.gz>` (`--profile` to rename the restored profile, `--trust-bundle` to restore its hooks/MCP servers/command settings/env without the confirmation prompt; required when there is no terminal).
- **Health / drift**: `ccpm doctor` (`--fix` prunes dangling shared-asset symlinks), `ccpm consolidate`, `ccpm default fingerprint update`, `ccpm default fingerprint check`.
- **Exit codes (for scripting)**: 0 = success (stderr warnings never change the exit code), 1 = command failed, 3 = partial failure (`ccpm import` or `ccpm sync` did some work but at least one profile/step failed), 4 = `ccpm doctor` found health issues (including a `config.json` it cannot load). (Code 2 is reserved for usage errors but not yet wired: flag/arg errors currently exit 1.) A mistyped subcommand of a group command (`ccpm config sett ...`) fails with `unknown command` and exits 1; a bare group (`ccpm config`) prints help and exits 0. `ccpm remove` and `ccpm uninstall` without `--force` and without a terminal exit 1 instead of silently cancelling.
- **Auth**: `ccpm auth status`, `ccpm auth refresh`, `ccpm auth backup`, `ccpm auth restore`.
- **Asset trees** (each has `add`, `remove`/`rm`, `list`/`ls`, `link`): `ccpm skill`, `ccpm agent`, `ccpm command`, `ccpm rule`.
- **MCP**: `ccpm mcp add|remove|list|import|auth` (`list --json` supported) with `--scope global|profile|project`, transports `stdio|http|sse`.
- **Plugins**: `ccpm plugin list|enable|disable|install|remove|gc` and `ccpm plugin marketplace add|remove|list`. `plugin remove` deletes only the plugin's own cache link under `<profile>/plugins/cache/` (older builds deleted whatever path `installPath` named). `plugin gc` aborts, naming the profile, if any profile's `installed_plugins.json` cannot be read (including a legacy v1 file), rather than deleting caches that profile may use. A plugin whose content changed without a version bump is cached as `<version>+<first 12 chars of the commit>` beside the old version.
- **Hooks**: `ccpm hooks add|remove|list`.
- **Permissions**: `ccpm permissions allow|ask|deny|remove|list|mode`.
- **Env**: `ccpm env set|unset|list`. At `ccpm run`, a profile env entry replaces the same variable inherited from the parent shell, and `--ccpm-env KEY=VALUE` replaces both. `CLAUDE_CONFIG_DIR` and `ANTHROPIC_API_KEY` are always computed by ccpm and replace inherited copies (before this fix an inherited copy from `ccpm use`, a system default or an exported key could win, so an npm-installed `claude` launched as the wrong profile).
- **Settings**: `ccpm settings set|get|apply|show|statusline|outputstyle`. `settings apply` refuses a patch that touches security-sensitive keys (permissions, hooks, env, and command-running keys such as `apiKeyHelper`, `awsAuthRefresh`, `awsCredentialExport`, `gcpAuthRefresh`, `otelHeadersHelper`, `fileSuggestion`, `subagentStatusLine`, `processWrapper`) unless `--i-know-what-this-does` is passed.
- **Sessions**: `ccpm sessions list <profile>` (with `--all`, `--limit N` — default 20 most recent, `--json`). Without `--all` it lists only the sessions started in the current working directory, the same scoping as `claude --resume`; `--all` lists every project the profile has worked in. The table columns are SESSION ID, LAST ACTIVE, PROJECT and FIRST PROMPT, sorted most recently active first (like `claude --resume`); `--json` gives `session_id`, `started` (the session's first timestamp), `last_active`, `cwd` and `first_prompt`. Subagent transcripts are not listed as sessions (they can't be resumed), transcripts Claude Code has pruned are skipped, printed text is sanitized of terminal control sequences, and a directory reached through a symlink (`/tmp` vs `/private/tmp`) matches its sessions. Older builds listed every subagent transcript as its own `agent-...` row, which pushed real sessions past `--limit`. (Before 0.7.0 the directory-scoped default found nothing for most paths, because ccpm encoded the directory name differently from Claude Code, so it only worked with `--all`. Fixed in 0.7.0.)
- **Usage**: `ccpm usage [profile]` reports token usage from the profile's Claude Code transcripts. On a terminal it opens an **interactive dashboard** (tabs Overview/Days/Models/Projects/Sessions, switch profile with `[`/`]`, cycle the time window with `w`, scroll with arrows, `q` to quit). For static/scriptable output use `--plain`, `--json`, or any of `--by-model`/`--by-project`/`--sessions`/`--all`/`--since <dur|date>` (these always print non-interactively). Default profile resolution matches `ccpm prompt`/`statusline` (active session, then default). `ccpm usage sync [profile]` refreshes the usage store without printing a report (it is what the opt-in `usage_tracking` SessionEnd hook runs).
- **Status line**: `ccpm statusline` (Claude Code invokes it as the profile's `statusLine` command; you don't normally run it yourself) and `ccpm statusline configure` (`--profile <name>`, `--row1 a,b,c`, `--row2 a,b,c`, `--off a,b,c`, `--reset`), which chooses which segments show and on which of the two rows. See the status line section below.
- **Import**: `ccpm import default` (with `--only skills,commands,rules,hooks,agents,settings,mcp,plugins`) and `ccpm import from-profile`.
- **Trust**: `ccpm trust add|remove|list` (manages which project dirs ccpm treats as trusted). Trust only affects ccpm's own view of a repo's `.claude/settings.json` / `settings.local.json` in `ccpm settings show` and the desktop app: for an untrusted project that view keeps only a short allowlist of inert display, editor and model keys (`model`, `theme`, `outputStyle`, `language`, ...). ccpm never writes project settings or MCP servers into a profile; Claude Code reads them from the repo itself behind its own workspace-trust prompt, so trusting a repo does not copy its hooks or MCP servers into the profile.
- **Config**: `ccpm config set <key> <value>` and `ccpm config get <key>`. Keys: `cascade_auto_adopt` (bool), `check_default_drift` (bool), `statusline` (bool — auto-inject a default statusLine on `ccpm run`; default true), `usage_tracking` (bool — inject a SessionEnd hook that keeps the usage store warm; default false/opt-in, `ccpm usage` works without it; setting it back to `false` uninstalls the hook on the next `ccpm run`), `default_dir` (read-only).
- **Shell**: `ccpm shell-init` (zsh, bash, fish, powershell) prints the `ccpm use` shell hook (in bash and zsh a failed `ccpm use`, such as an unknown profile, returns non-zero; the fish and PowerShell hooks were broken in older builds and now work); `ccpm completion bash|zsh|fish|powershell` prints a Cobra completion script (with profile-name completion for run/use/remove/rename/set-default/clone/export).
- **Diff**: `ccpm diff <profile-a> <profile-b>` compares profile-scoped assets, settings-fragment keys, env var names (values never shown), MCP servers, and installed plugins.
- **Global flags**: `--log-level debug|info|warn|error` (default warn) on every command; `debug` traces cascade and lock activity.
- **Lifecycle**: `ccpm uninstall` (`--force`/`-f` skips the confirmation). It deletes every profile and `~/.ccpm/`, API keys and OAuth logins in the OS keychain, vault backups and the vault master key, and clears the system-wide default set by `set-default` (macOS). It does not remove the `ccpm` binary or your shell hook line.
- **Version**: `ccpm --version` (root flag) or `ccpm version`; `ccpm version --check-latest` makes an explicit opt-in request to the GitHub releases API (cached 24h) to report whether a newer release exists — this is the only network call in the CLI and never happens without the flag. It compares against the newest stable **CLI** release (`v*` tags); desktop-app releases (`desktop-v*`), drafts and pre-releases are skipped. Before 0.7.0 it could compare against a desktop release and wrongly report every install as up to date.

There is **no** `ccpm copy`, `ccpm drift`, `ccpm vault`, or `ccpm update` subcommand. Profile duplication is `ccpm clone`; portable export/restore is `ccpm export` / `ccpm import-bundle`. Vault backup/restore (encrypted credential backup) is exposed via `ccpm auth backup|restore`. Drift detection is `ccpm default fingerprint`.

## Run flags intercepted by ccpm

`ccpm run <profile> [args...]` forwards unknown flags to claude without a `--` separator. Five flags are intercepted before they reach claude: `--ccpm-env KEY=VALUE` (repeatable, one-shot env override), `--no-auto-adopt` (skip the host-asset cascade scan), `--no-statusline` (skip injecting the default statusLine for this launch), `--help`, `--version`. To forward `--help` or `--version` to claude, use `ccpm run <profile> -- --help`.

## Default profile (IDE / GUI)

`ccpm set-default <name>` pins a profile as the machine-wide default for **every** `claude` launch — the integrated terminal, IDE extensions (Cursor, VSCode, Antigravity), and any GUI app that spawns `claude` — not just shell-bypassing launches. It is the way to set a default for tools that don't go through the `ccpm use` shell hook. Call it without a name in a TTY for a profile picker.

For an **OAuth** profile on macOS it does three things: copies the profile's namespaced keychain entry into the default slot (folding the previous default's slot back into its own profile first, but only when those tokens are fresher, so a recent `ccpm run <p> claude /login` is never clobbered), syncs identity fields (`oauthAccount`, `userID`) into `~/.claude.json` so the welcome banner shows the right account, and registers a machine-wide `CLAUDE_CONFIG_DIR` via `launchctl setenv` plus a user-level LaunchAgent (`com.ccpm.default-config-dir`) that re-applies it at every login. The `launchctl setenv` part is what extends the default to terminals and GUI apps, and also works around a Claude Code v2.1.x startup-refresh bug that 401s when `CLAUDE_CONFIG_DIR` resolves to bare `~/.claude`.

For an **API-key** profile, `set-default` instead clears any machine-wide `CLAUDE_CONFIG_DIR` pin, removes the default-slot OAuth entry, and writes `ANTHROPIC_API_KEY` into `~/.claude/settings.json`'s `env` block (so terminal and agent invocations use that key). The VSCode/Antigravity sidebar cannot show API-key logins as "signed in," but `claude` invocations do use the key.

Removing the default profile with `ccpm remove` (or running `ccpm uninstall`) clears the system default the same way `unset-default` does, including an API-key default's `ANTHROPIC_API_KEY` in `~/.claude/settings.json`; `ccpm rename` of the default profile re-points the default at the new directory. Older builds left GUI/IDE `claude` pointed at the deleted or old directory. `set-default` also writes `~/.claude.json` through a symlink (a dotfiles-managed file stays a symlink).

Already-running IDE windows need one restart to pick up the new env; future launches and future logins are automatic. `ccpm unset-default` removes the LaunchAgent, runs `launchctl unsetenv`, strips the `ANTHROPIC_API_KEY` env block, and clears the default pointer. On Linux and Windows the keychain/credentials and identity sync still apply; the `launchctl` machine-wide mechanism is macOS-only for now (terminal use on those platforms is covered by the `ccpm use` shell hook).

## Authentication

- **OAuth**: browser flow via `claude /login` in profile context. macOS uses Keychain under a **namespaced** service derived from `CLAUDE_CONFIG_DIR` (Claude Code **v2.1.56+** required).
- **API key**: stored via OS keychain (`go-keyring`), service `ccpm`, account `<profile>`.
- **macOS keychain size limit**: ccpm writes Claude Code's keychain entry through the `security` CLI, which cuts input at 4 KB. An OAuth payload over about 4 KB (possible once several MCP servers hold OAuth tokens) now fails with `OAuth payload too large for the macOS security CLI (4 KB line limit); keychain left unchanged` in `set-default`, `clone`, `rename` and `auth restore`. Older builds silently wrote a truncated, broken copy over the good entry. There is no workaround inside ccpm yet; the existing login is left intact.
- **Removing a profile** deletes its API key and its OAuth keychain entry, so `ccpm add <same name>` starts signed out.
- **Vault**: encrypted backup under `~/.ccpm/vault/<profile>.enc` (AES-256-GCM, master key in OS keychain). Created with `ccpm auth backup <name>`, restored with `ccpm auth restore <name>`. The master key is created only when none exists: a locked keychain or dismissed prompt makes the command fail rather than replace the key (older builds replaced it, which made existing backups undecryptable), and `auth restore` never creates one.

## Backup, clone, and migrate profiles

- **`ccpm clone <source> <new>`** duplicates a profile in place (skills, agents, commands, rules, hooks, MCP fragments, plugins, settings, manifest entries, and, unless `--no-auth`, credentials). `ccpm import from-profile` copies the same way (older builds skipped profile-scoped skills and fragments, and `import from-profile` failed on most real profiles). `ccpm rename` carries the settings/MCP fragments and manifest refs to the new name, and `ccpm remove` deletes them, so a later `ccpm add <old name>` starts clean (older builds let it inherit the removed profile's MCP servers and their tokens; `add` now also clears such leftovers). For an OAuth clone the new profile **shares the source account's tokens**, so refresh-token rotation in one staleness the other; for a long-term clone against the same account prefer `--no-auth` and run `ccpm auth refresh <new>` to give it its own login. API-key clones have no such caveat.
- **`ccpm export <profile>`** bundles a profile into a portable `.tar.gz` (`-o`/`--output` to choose the path, default `<profile>.ccpm.tar.gz`): its `settings.json` and plugin metadata, its skills, agents, commands, rules and hooks (content behind links into `~/.ccpm/share` is copied in; links elsewhere, such as `~/.claude` host assets, are skipped and listed), and its ccpm settings, owned-keys and MCP fragments (under `.ccpm-bundle/` in the archive). **Session history is excluded by default** (`projects/` transcripts, `todos/`, `shell-snapshots/`, `history.jsonl`, `file-history/`, ...) because it can contain pasted secrets; `--include-history` includes it for a same-user machine move. **Credentials are excluded by default** because keychain tokens are machine-bound and `.credentials.json` / `.claude.json` hold secrets; use `--include-credentials` only for a trusted same-user move. A bundle made with either flag is sensitive, and even a default bundle carries hooks, MCP server definitions and settings env values, so review it before sharing. Plugin caches are not bundled; reinstall plugins on the new machine.
- **`ccpm import-bundle <file.tar.gz>`** restores a profile from an export bundle (path-traversal-safe, with extraction capped at 512 MiB per file and 4 GiB total). Before restoring, it lists every hook command, MCP server, command-valued setting (`statusLine`, `apiKeyHelper`, ...) and settings `env` key in the bundle and asks for confirmation (default no). Without a terminal it refuses unless `--trust-bundle` is passed. Malformed bundle JSON is refused. The restored profile takes the bundle's original name unless `--profile <name>` overrides it. If the bundle had no credentials (the default), authenticate afterward with `ccpm auth refresh <name>`. Bundles from older versions still import.

## Shell prompt integration

`ccpm prompt` prints the active profile name so a shell prompt (PS1, starship, powerlevel10k) can show which Claude Code account a terminal is bound to. Resolution order: `$CCPM_ACTIVE_PROFILE` (set by `ccpm use`) → `$CLAUDE_CONFIG_DIR` (matched back to a known profile dir) → the configured default, **only** with `--show-default`. It prints nothing (exit 0) when no profile is active. `--format '%s'` wraps the name (must contain a single `%s`).

`ccpm statusline` is the in-TUI status line for a launched session — it shows **which profile is running** plus usage/limits at the bottom of the Claude Code window. It reads Claude Code's status JSON on stdin and renders **two rows** (Claude Code displays each printed line as its own row): row 1 is the session — `⬢ work · claude-code-profile-manager/ccpm · ⎇ feat/history-tab · Opus 5 · ctx 34%` (profile, repo with the subdirectory you are in, git branch, model, context used); row 2 is the budget — `effort high · 5h 42% ↺16:15 · 7d 12% ↺Mon 8 Sep 08:25 · $1.23` (reasoning effort, the usage windows with the date each renews, session cost). The split is by what you consult them for, not by how fast they change: row 1 answers "what am I talking to, and where", row 2 answers "how much is left". The `5h`/`7d` segments are the **percentage used** of the rolling subscription usage windows — matching Claude's own `/usage` panel (Pro/Max accounts only; they appear after the first API response and are absent for API-key profiles). A renewal falling on today's date shows a bare clock; one on any other date gives the day and date (`↺Mon 8 Sep 08:25`). That is a calendar-day rule, not a distance rule — an evening five-hour window that resets after midnight will carry tomorrow's date even though it is only hours away. The `effort` segment appears only for models that report a reasoning-effort level. Every segment drops out when its data is absent, and a row with nothing to say is not printed at all — an API-key profile outside a git repo prints `⬢ work · myproject · Opus 4.8` and `$0.12` — no branch, no usage windows, but the directory still shows, because the workspace segment falls back to the directory name whenever there is no repo. A row disappears only when every segment on it is absent or switched off. Those are the **defaults** — which segments appear, and on which row, is configurable (see below). The branch is read from `.git/HEAD` directly rather than by shelling out to git, because the status line re-runs on every assistant message. The line is **ANSI-coloured** by default — the `5h`/`7d` percentage shades green→amber→red as remaining headroom shrinks; set `NO_COLOR` for plain text. The `$…` segment is the API-equivalent cost estimate of the session, not a subscription charge. `ccpm run` injects this automatically as the profile's `statusLine` when the profile has none of its own — it never overwrites a statusLine you set in `~/.claude/settings.json`, a profile, or a trusted project. Turn the auto-injection off persistently with `ccpm config set statusline false`, per-launch with `ccpm run <profile> --no-statusline`, and remove an already-injected one with `ccpm settings statusline "" --profile <name>`.

**Choosing the segments.** `ccpm statusline configure` opens an interactive picker: it asks which segments go on row 1, then which of the rest go on row 2, and anything unpicked is switched off. It prints the resulting status line against sample data so the effect is visible immediately. The nine segment keys are `profile`, `workspace`, `branch`, `model`, `context`, `effort`, `five_hour`, `seven_day`, `cost`. The picker is also offered automatically the first time you run `ccpm config set statusline true` (which is only about whether the status line is injected at all — it is a separate switch from which segments it shows).

Layouts have two scopes. Without `--profile`, `ccpm statusline configure` sets the **global default** for every profile; with `--profile <name>` it sets an **override for that profile alone**, which wins over the global. `ccpm statusline configure --reset --profile <name>` drops the override so the profile follows the global again; `ccpm statusline configure --reset` restores the built-in default. Layouts are stored in `~/.ccpm/config.json` — `settings.statusline` for the global, `profiles.<name>.statusline` for an override — each as `{"row1": [...], "row2": [...], "off": [...]}`. Order within a row is the stored order and is fully editable: the desktop app gives each segment move-up/move-down controls, `--row1 a,b,c` is written in the order given, and the interactive picker preserves an order you already have (segments that stay on a row keep their relative positions; newly added ones are appended) rather than re-sorting to catalog order.

For scripts (and for the desktop app, which shells out to exactly this) the rows can be passed explicitly instead of prompting: `ccpm statusline configure --row1 profile,model --row2 cost --off workspace,branch,context,effort,five_hour,seven_day`. Every segment must be listed exactly once across the three flags — an incomplete list is rejected rather than filled in, because a segment mentioned nowhere is treated as *newly introduced* and placed at its default (that is how a layout saved by an older ccpm picks up a segment added later). Running `ccpm statusline configure` with no flags and no terminal is an error naming those flags.

Switching every segment off is allowed and prints nothing at all. Turning a segment on never invents data: enabling the 5h window on an API-key profile still shows nothing, because Claude Code sends no rate limits for it. Switching `branch` off also stops ccpm reading `.git/HEAD` on every assistant message.

In the **desktop app**, the same thing lives in the **Settings** tab under "Status line": segments are grouped under Row 1 / Row 2 / Hidden in the order they render, each with an Off / Row 1 / Row 2 selector and move-up/move-down arrows, below a live preview of both rows, with a scope switch between the global default and this profile's override. Moving a segment to another row appends it at that row's end. It writes by shelling out to `ccpm statusline configure`, so the desktop app needs a `ccpm` CLI new enough to have that command (0.7.0 or later). You don't normally call `ccpm statusline` yourself; Claude Code invokes it.

## Usage tracking (`ccpm usage`)

`ccpm usage [profile]` reports per-profile token usage by reading the Claude Code session transcripts a profile accumulates under `<profileDir>/projects/**/*.jsonl`. It shows raw token totals (input, output, cache-write, cache-read) — **no dollar cost is computed** (transcripts carry no price, and a subscription's real cost is unrelated to API-equivalent pricing). On a TTY it opens an interactive dashboard (tabbed Overview/Days/Models/Projects/Sessions, `[`/`]` switch profile, `w` cycles the time window, arrows scroll, `q` quits); `--plain` prints the static report instead. The static view prints totals, a GitHub-style **contribution heatmap in amber** (intensity by tokens/day; set `NO_COLOR` for plain glyphs), and a per-model breakdown; `--by-project`, `--by-model`, and `--sessions` swap the body, `--since <dur|date>` windows it, `--all` aggregates every profile, and `--json` emits a stable snake_case contract. Counts are deduplicated by `(message.id + requestId)` with the **largest token snapshot winning** — Claude Code writes each response as several transcript lines sharing one `message.id`, sometimes with growing usage snapshots, so a naive sum over-counts ~3× and a first-seen dedup can under-count. `ccpm usage` reports token counts only (no dollar cost); the desktop app's Usage tab additionally shows an **API-equivalent cost estimate** and a live **5-hour block** monitor, and the History tab shows a per-session cost estimate (no block monitor) (see below). Data is maintained incrementally in a ccpm-owned `<profileDir>/usage/` store (ingest cursor + session index + daily index); each run reads only new transcript bytes since the last. By default the store refreshes lazily whenever you run `ccpm usage`; enable `ccpm config set usage_tracking true` to also inject a `SessionEnd` hook (`ccpm usage sync`) that keeps it warm after every session (the injected hook preserves any `SessionEnd` hooks you already declare in `~/.claude/settings.json`, and setting the key back to `false` removes it again) (opt-in because it adds a hook + per-session process; the lazy refresh already keeps `ccpm usage` accurate without it). Transcript reading skips anything under `projects/` that is not a regular file (a symlink such as one to `/dev/zero` used to make `ccpm usage`, the SessionEnd hook, the TUI and the desktop Usage tab read without bound) and caps a single transcript line at 8 MiB. The desktop Usage tab's current 5-hour block reads only the last 10 hours of transcripts and loads once per profile, so it opens in a fraction of the time it used to.

## MCP

- **Isolation invariant**: merge reads only `share/mcp/global.json` and `share/mcp/<profile>.json`. It never iterates arbitrary files in `share/mcp/`.
- Materialized MCP lives in **`<profile>/.claude.json#mcpServers`**, not `settings.json`.
- **Scopes**: global, profile, project (`--scope` or legacy `--global` / `--profile`). Transports: stdio, http, sse. `ccpm mcp auth <name> --profile <p>` runs native Claude scoped to the profile to complete OAuth.
- **Removal**: `ccpm mcp remove <name> --scope profile --profile <p>` refuses with `MCP server "<name>" is not installed in profile "<p>"` when that profile does not hold the server (older builds reported success and dropped the manifest record while the server stayed in the other profile). Removing a server, including the last one, now also removes it from the profile's `.claude.json` on the next `ccpm run`/`use`/`sync`.
- Project `.mcp.json` and project `mcpServers` are read by Claude Code itself from the working directory; ccpm does not copy them into the profile.

## Settings merge (low to high, higher wins)

What ccpm writes into `<profile>/settings.json` at launch (profile-scoped sources only):

1. Keys already in the profile's `settings.json` that ccpm did not write (what Claude Code or you set in a session, such as `/model` or a permission rule). These are kept.
2. Host `~/.claude/settings.json`.
3. ccpm profile fragment `share/settings/<profile>.json`.
4. **Owned-keys** sidecar (values explicitly set via `ccpm settings set --profile`).

On top of that, Claude Code itself applies (ccpm shows these in `ccpm settings show` and the desktop app, but **never writes them into the profile**):

5. Project `./.claude/settings.json`.
6. Project `./.claude/settings.local.json`.
7. Enterprise managed-settings (highest): `/Library/Application Support/ClaudeCode/managed-settings.json` (macOS), `/etc/claude-code/managed-settings.json` (Linux), `C:\Program Files\ClaudeCode\managed-settings.json` (Windows; older ccpm looked under `C:\ProgramData\ClaudeCode` and never loaded it), plus `managed-settings.d/*.json` drop-ins.

Older builds copied project and managed settings into the profile, where they stayed and applied in every later session in any directory (including command-running keys from an untrusted repo). **Removals propagate**: ccpm records sha256 fingerprints (never values) of what it wrote in `<profile>/.ccpm-materialized.json`, so a setting or MCP server removed at its source (`ccpm mcp remove`, `ccpm settings unset`, a key deleted from `~/.claude/settings.json`) disappears from the profile on the next launch, while values you or Claude Code changed are kept. Keys an older ccpm already copied into a profile look like your own data and are kept; remove them by hand if unwanted. Arrays merge by replacement.

There is **no** ccpm-managed global settings fragment; the shared baseline is the host `~/.claude/settings.json` directly.

## Host asset cascade

Optional auto-adopt from `~/.claude/{skills,agents,commands,rules,hooks,plugins}` into every profile (`scope=host` in the manifest). **Profile-local always wins** over host, and a profile's own (non-symlink) skill or agent folder is never deleted to make room for a host entry of the same name (older builds could delete it). Opt out: `ccpm config set cascade_auto_adopt false` or `--no-auto-adopt` on `run` / `sync`.

## Desktop app (CCPM Desktop)

An optional native desktop GUI for managing profiles, alongside the CLI (the CLI remains the primary interface). Built with **Wails** (Go backend + native OS webview) in the same Go module, so it reuses ccpm's own engine for reads and shells out to the `ccpm` CLI for writes (same lock/keychain/atomic/validation — the GUI can't corrupt state the CLI wouldn't). Local-first, no signup.

- **What it does**: left sidebar of profiles + a tabbed view per profile — **Overview** (asset counts, details), **Cascade** (the effective host→global→profile config with per-asset/per-setting provenance badges and override/shadow hints), **Assets** (add/remove skills/agents/commands/rules/hooks), **MCP & Plugins** (list + add/remove MCP, install/remove + enable/disable plugins), **Permissions** (allow/ask/deny rules, default mode, env vars), **Settings** (edit effective settings as JSON via `ccpm settings set`, plus the **Status line** and **Usage notch** sections described in this document), **Usage** (native amber heatmap + token totals + by-model/project, PLUS an **API-equivalent dollar-cost estimate** and a live **"current 5-hour block"** card with burn rate, time-left, and projected cost — inspired by ccusage; cost is estimated from public API list prices, not subscription billing), **History** (browse, read and search this profile's past Claude Code sessions — see below), and **Health** (`ccpm doctor` output). Profile actions: Run, Clone, Rename, Delete, Open folder. It auto-refreshes when the CLI or Claude Code change files underneath it. The **MCP & Plugins** tab lists only the selected profile's MCP servers (older builds listed every profile's profile-scoped servers, and removing one of another profile's servers did nothing useful). Removing an MCP server, uninstalling a plugin, removing a permission rule and unsetting an env var ask for confirmation first. Env values on the Permissions tab are masked until revealed per row. Error toasts show the full CLI message. A malformed `settings.json` is reported on the Permissions, Settings and Cascade tabs instead of making them look empty, and a missing, outdated or timed-out CLI is reported on the MCP tab. Three built-in themes — **Graphite** (default, warm dark grey), **Midnight** (deep blue-black), and **Light** — switch from the title-bar theme button and persist across launches.
- **Usage notch (macOS)** (formerly the "usage rail"): an optional codenotch-style notch that grows out of a screen edge, showing one ring per profile with that profile's Claude usage — the big outer ring is the **main window** (the **5-hour** window by default, or the **weekly/7-day** one if chosen), the thin inner ring the other, coloured by remaining headroom on the same thresholds as the CLI statusline (healthy at >=50% left, tightening at >=20%, near-limit below). Hovering a ring opens a detail callout: account and plan (shown as e.g. "Max 5x", not the raw rate-limit tier), how old the reading is, and per window a reset time, a bar, and the percentage used. The callout closes shortly after the pointer leaves (older builds could leave it stuck on screen), and it stays open with fresh numbers when a refresh lands under a resting pointer. A window whose reset time has passed reads 0% until the next reading arrives. The notch always appears on the primary display (the one with the menu bar), not whichever display has the focused window; a hidden notch ignores the pointer. With many profiles (10 or more) on a short side edge, the notch shows as many rings as fit. Configured in the **Usage notch** section of the **Settings** tab (the old title-bar gauge button is gone): a master **Show usage notch** switch, and only while it is on, **Reveal** (On hover / Always open), **Position** (Top / Left / Right / Bottom; Top joins the Mac's camera notch on displays that have one), **Main ring** (5-hour / Weekly), **Show percentage** (off hides the figure under each ring and gives the rings the room back; useful on the top edge with several profiles, where the labels shrink to a few points), and a per-profile switch. Defaults on a fresh install: switched on, reveal on hover, right edge, 5-hour main ring, percentage shown, every profile enabled (a newly created profile appears without having to find its switch). The notch is only on screen while at least one enabled profile exists. Turning the notch off and back on restores the reveal and other choices. The section shows a hint when no profile has a reading yet. Settings are stored in `~/.ccpm/desktop.json` (`railOn`, `railMode`, `railEdge`, `railPercent`, `railMain`, `railProfiles`); an older file with `railMode: "hidden"` loads as switched off. In hover mode the notch folds to a slim pill at the edge and opens when the pointer reaches it; **Reduce Motion** turns the animation into a jump. The notch is a native AppKit panel (Wails v2 cannot open a second window), it never takes keyboard focus, and it stays visible across Spaces and over full-screen apps.
- **Where the notch's numbers come from (important)**: Claude Code sends `rate_limits.five_hour` and `rate_limits.seven_day` to `ccpm statusline` on stdin; ccpm caches them per profile and the notch reads that cache. **No API call is made and no credentials are read.** The consequence is that a profile's reading only refreshes when that profile's statusline renders — i.e. when you actually use Claude Code on it — so the callout always states the reading's age and labels it stale past 30 minutes. A profile that has never run Claude Code shows an empty ring with "—" for its percentage and says "No reading yet", and so does a profile whose own custom `statusLine` replaces ccpm's (or one launched with the status line auto-injection turned off), because only `ccpm statusline` writes the cache; the notch never draws a 0% arc for missing data, because an empty ring would read as plenty of headroom. **Only subscription plans report limits** (Max/Pro); an API-key or other non-subscription profile shows "Plan does not report limits" and will never populate.

- **History tab (desktop, per profile)**: lists every Claude Code session the profile has run, newest first. Each row shows a **title** (Claude Code's own generated `ai-title` when the transcript has one, otherwise the first real user prompt, capped at 200 characters), the full project path, the git branch, the model, a **responses** count (deduplicated usage-bearing assistant lines — deliberately not the same number as the reader's turn count), a turn count, tokens, and an estimated cost summed **per model** so a session that switched models is priced correctly. A single query box has a scope switch: **Filter list** narrows the rows by project, branch and title client-side; **Search transcripts** runs a full-text scan. Sessions whose transcript Claude Code has since pruned still appear (their token history is real) but are marked and cannot be opened.
  - **Reader**: clicking a session renders the conversation. Tool calls fold into one-line chips showing the identifying argument (a Bash command, an Edit's path) and expand to the full payload on demand; thinking blocks and subagent (sidechain) turns are behind toggles that disable when a session has none. Turns are fetched in pages of 200, so a 77 MB transcript with 10,000+ turns opens without freezing. Navigation is by **prompt** (previous/next plus a prompt outline), not by turn number. Block types ccpm does not recognise render as a visible "unrecognised block" placeholder rather than being dropped, so a Claude Code format change is visible rather than silent. The reader is a point-in-time read — transcripts are not watched, so a running session's later turns appear on refresh. A transcript that cannot be opened — pruned, unreadable, or outside the profile — says so with a Retry, rather than rendering as an empty conversation; a blank page and a real failure used to look identical. A search hit in a transcript written since the tab last listed (a subagent file a running session just spawned) resolves correctly: the index is rebuilt on demand rather than refusing the hit.
  - **Search**: a live streaming scan with **no full-text index** — transcript contents are read on every search, so there is no content index to build or to go stale. (ccpm does keep a small per-profile *history sidecar* at `<profileDir>/usage/history.json` holding session titles, models, token totals and paths; it is metadata only, is rebuilt automatically, and is never consulted for matching text.) Matching is case-insensitive literal substring of the whole query (not regex, not word-AND). Default scope is your prompts, Claude's replies, and **tool inputs** (commands, file paths, patterns); **tool output is opt-in** via an "include tool output" toggle, because tool results are the bulk of a transcript by volume and are where pasted credentials and secrets-file dumps end up. Thinking blocks are never searched. Results are snippets grouped by session, newest first, and clicking one opens the reader at that message — force-expanding a collapsed tool chip or enabling the subagent toggle if that is where the match lives. When a default-scope search finds nothing, it offers the wider scan rather than showing a bare empty state. Scanning is bounded: each session contributes at most a handful of hits and the scan stops there. When that bound actually cut the scan short the count is shown as a floor ("31+ matches") and the result is marked truncated; a search that happened to fill its budget exactly and had nothing more to find reports a plain total. Search is scoped to the selected profile.
  - **Resume**: relaunches a session in Terminal via `ccpm run <profile> -- --resume <id>`, `cd`-ed into the directory the session was originally started in (its first recorded cwd, which is what `claude --resume` matches on). Sessions whose directory no longer exists report that instead of opening a broken window.
  - **Where the data comes from**: the same `<profileDir>/projects/**/*.jsonl` transcripts usage reads, plus an additive sidecar index at `<profileDir>/usage/history.json` holding each session's title, model, per-model token tally and real transcript path. The sidecar is rebuildable from nothing and **never touches the usage token store** — no schema bump, no re-ingest, and no risk to existing token history. Subagent transcripts (`subagents/**/agent-*.jsonl`, roughly three quarters of the files in a profile) are **not listed as their own sessions** — that would bury the real ones — but they **are searched**, and their hits are attributed to the session that spawned them and marked `subagent`. Clicking one opens that subagent's transcript. This matters because Claude Code does *not* copy a subagent's conversation back into its parent: measured across 77 real parent transcripts, `isSidechain` is present on 68,167 lines and false on every one. Their tokens are folded into the parent session's totals so History reconciles with the Usage tab.
- **First run**: detects existing profiles and opens to the list; with zero profiles it shows a one-screen explainer plus Create / Import buttons.
- **Auth**: in-GUI OAuth is not implemented yet — creating a profile or importing `~/.claude` opens a Terminal running the proven `ccpm add` wizard to complete sign-in.
- **One-line install (recommended)**: `curl -fsSL https://raw.githubusercontent.com/nitin-1926/claude-code-profile-manager/main/scripts/install-desktop.sh | sh`. It finds the newest `desktop-v*` release, picks the arm64 or amd64 build, verifies its SHA-256 against `checksums.txt`, and installs `CCPM.app` to `/Applications` (override with `CCPM_APP_DIR`), quitting that copy first if it is running (a CCPM running from anywhere else is left alone). Because `curl` does not set the quarantine flag, the app opens with no Gatekeeper prompt at all. If a user asks why other unnotarized-looking apps open after a confirmation while CCPM says "damaged": those apps are notarized (their developers pay for an Apple Developer ID); a browser-downloaded app that is only ad-hoc signed is refused outright, which macOS 15+ words as "damaged".
- **Download**: prebuilt `.dmg`s are published on GitHub Releases under the desktop-scoped tag list `https://github.com/nitin-1926/claude-code-profile-manager/releases?q=desktop-v&expanded=true` (do NOT use `/releases/latest` — that is meant to resolve to the CLI release, which has no `.dmg`) — a separate ~3–4 MB build per chip: **Apple Silicon** (`CCPM-<version>-arm64.dmg`) and **Intel** (`CCPM-<version>-amd64.dmg`). Open the `.dmg` for your Mac and drag **CCPM** into **Applications**. Because the app is **not notarized** yet, macOS Gatekeeper blocks the first launch. On **macOS 15 Sequoia and later** right-click → Open no longer bypasses this, and macOS may say the app **"is damaged and can't be opened"** — it is NOT damaged (the release is checksummed and ad-hoc signed; macOS just can't verify the developer). The fix is to clear the download quarantine flag once: `xattr -dr com.apple.quarantine /Applications/CCPM.app`, then open it normally. On macOS 14 and earlier, right-click → **Open** works. If a user reports the app as "damaged" or "corrupted", this is the answer — do not tell them to re-download. The app uses the `ccpm` CLI for write actions, so the CLI must also be installed (it's resolved from standard locations like Homebrew/`/usr/local/bin`/npm-global even though a GUI app doesn't inherit your shell PATH).
- **Auto-updates**: the app checks GitHub Releases on launch and, when a newer build exists, shows a bottom-right "Update available" prompt with an **Update now** button. It downloads the new build itself, verifies its SHA-256, and **swaps the app in place, then relaunches — no re-dragging to Applications and no repeat of the Gatekeeper prompt** (self-downloaded builds aren't quarantined). The one-time quarantine step only applies to the very first install. If the app cannot replace itself (its folder is not writable by the current user, e.g. a non-admin account with `/Applications`, or macOS App Translocation is running it from a temporary read-only location because it was never moved), it refuses with a message before downloading instead of quitting; for translocation, move CCPM to `/Applications`, open it from there, and update again. If the swap fails midway, the old app is restored and reopened. Updates are integrity-checked over HTTPS (Apple notarization / signed updates are a later hardening step).
- **Versioning & release**: the desktop app versions **independently of the CLI** — it ships on `desktop-v*` git tags (the CLI uses `v*`), built by a dedicated `Desktop Release` GitHub Actions workflow that publishes per-arch `.dmg` + `.app.zip` + `checksums.txt`. The running version is baked into the binary at build time.
- **Build/run**: requires the Wails CLI (`go install github.com/wailsapp/wails/v2/cmd/wails@latest`), then `cd ccpm && make desktop` produces `desktop/build/bin/CCPM.app`; `make desktop-dev` runs a hot-reload window. The app is **ad-hoc signed and not notarized** for now, so a downloaded copy needs the one-time quarantine step above; a copy you build locally is not quarantined and opens directly.
- **Status**: the desktop app is newer/secondary to the CLI; if unsure about a desktop-only detail, prefer pointing users at the CLI equivalent.

## Platforms

- **macOS**: verified path for OAuth isolation and keychain. The desktop app targets macOS first (the Run/create/import Terminal bridges are macOS-only; other OSes get a copyable command).
- **Linux / Windows**: ship and cross-compile; some OAuth / keychain paths are **experimental** until verified on real hosts. Windows may fall back to **copy** instead of symlink without Developer Mode (`~/.ccpm/.windows-copy-fallback` marker).

## Privacy

No telemetry; no remote calls from the CLI itself. Secrets are not logged in plaintext.

## Ask Me guardrails

- The docs site's Ask Me endpoint accepts only same-origin JSON POST bodies (verified via `Origin` or same-host `Referer`) with a string `question`.
- Questions are trimmed, length-capped, stripped of control characters and zero-width / BOM characters, and rejected when they contain obvious prompt-injection framing, HTML-comment framing, script-like markup, JavaScript URLs, or requests to reveal hidden/system prompt content.
- Requests are rate-limited per detected client IP. The Portkey API key and virtual key stay server-side; upstream errors are never echoed back to the client verbatim.
- Backend flow: the system prompt lives in code (not a Portkey saved prompt). The server sends a **system + user** message (this markdown as the trusted context, plus the user's `question`) to Portkey **`chat/completions`** routed by **`PORTKEY_VIRTUAL_KEY`** (the Gemini integration), and streams the reply token by token. The free **`gemini-2.5-flash-lite`** model is used by default (override via `PORTKEY_MODEL`).
- Answers are grounded by this checked-in context (capped at 64 KB). The client renders returned markdown through a sanitizer before display; HTML, scripts, styles, and inline event attributes are stripped.

## Troubleshooting pointers

- **MCP tools missing**: confirm servers appear under `<profile>/.claude.json#mcpServers` after `ccpm use` / `ccpm run`.
- **IDE shows wrong account after `set-default`** (OAuth): re-run `set-default` on a current binary and confirm `~/.claude.json` identity fields match the profile.
- **First-line health check**: `ccpm doctor` (auth, drift, symlinks, cascade). `ccpm doctor --fix` prunes dangling shared-asset symlinks.
- **Broken symlinks**: `ccpm doctor` detects them; `ccpm doctor --fix` prunes dangling shared-asset symlinks (deeper drift: `ccpm consolidate --fix`).
- **IDE still on the wrong account after `set-default`**: already-running IDE windows need one restart to pick up the new `CLAUDE_CONFIG_DIR`; future launches are automatic.
- **Running sessions don't see a change**: `set-default`, `rename`, and `remove` do not affect already-running Claude Code sessions — restart the session (and IDE window).
- **Claude Code too old (macOS OAuth)**: needs v2.1.56+ for per-profile keychain isolation; `ccpm doctor` reports the installed version.
- **Project settings missing from `ccpm settings show`**: ccpm's view of an untrusted repo keeps only inert display/editor/model keys; run `ccpm trust add` in that directory to see the rest. Claude Code itself still applies the repo's `.claude/settings*.json` and `.mcp.json` (behind its own trust prompt); ccpm never copies them into the profile.
- **A new profile had another profile's MCP servers or settings**: older ccpm left a removed profile's settings/MCP fragments behind, and `ccpm add` with the same name inherited them (including MCP env tokens). Current builds delete them on `remove`, carry them on `rename`, and clear leftovers on `add`. On an older build, delete `~/.ccpm/share/mcp/<name>.json` and `~/.ccpm/share/settings/<name>.json` (and `<name>.owned.json`) before re-adding.
- **A removed MCP server or setting keeps coming back**: older builds never removed anything from a profile once it got in. Current builds propagate removals on the next `ccpm run`; entries an older ccpm already copied in are treated as your own data, so delete them from `<profile>/settings.json` or `<profile>/.claude.json` by hand once.
- **`ccpm import-bundle` refuses in CI / a script**: with no terminal it will not restore a bundle's hooks, MCP servers, command settings or env without `--trust-bundle`. Pass it only for a bundle you made or trust; on a terminal you are asked instead.
- **`ccpm export` bundle has no transcripts**: session history is left out by default; add `--include-history` (and treat the bundle as private).
- **`set-default` / `clone` / `rename` / `auth restore` fails with "OAuth payload too large"** (macOS): the profile's keychain login is over the 4 KB the `security` CLI accepts, usually because several MCP servers hold OAuth tokens in it. ccpm refuses rather than writing a truncated copy, and the existing login is untouched. Not fixable inside ccpm yet.
- **`ccpm run <b>` started as a different profile, or used the wrong API key**: older builds let an inherited `CLAUDE_CONFIG_DIR` / `ANTHROPIC_API_KEY` (from `ccpm use`, `set-default`, an exported key, or a Claude Bash tool) win for npm-installed `claude`. Upgrade; ccpm now replaces inherited values.
- **`ccpm remove` / `ccpm uninstall` fails with "stdin is not a terminal"**: add `--force` in scripts.
- **Desktop MCP tab shows fewer servers than before**: it now lists only the selected profile's servers; older builds showed every profile's.
- **Desktop update says it cannot write the app folder or is running from a temporary location**: install or move CCPM into `/Applications` as a user who can write there, open it from there, and update again, or download the new build from the release page.
- **Usage notch shows "—" / "No reading yet"**: readings come only from ccpm's own status line. Launch the profile with `ccpm run` (which injects `ccpm statusline` when the profile has no `statusLine` of its own) and send a message. A profile with a custom `statusLine`, or with the auto-injection off (`ccpm config set statusline false` / `--no-statusline`), never records readings. API-key and other non-subscription profiles never report limits.
- **`ccpm sessions list` shows nothing**: without `--all` it only lists sessions started in the current directory; pass `--all` to see every project. On ccpm older than 0.7.0 the directory-scoped default found nothing for most paths; upgrade.
- **`ccpm version --check-latest` says up to date but a newer CLI exists**: versions before 0.7.0 could compare against a desktop-app release. Upgrade once (npm / curl / go install) and the check is correct from then on.
- **Status line segments**: the status line IS configurable. Run `ccpm statusline configure` (add `--profile <name>` for one profile only), or use the Settings tab's Status line section in the desktop app.
